01 · THE PROJECT

More than a transcription.

The conversation follows an intake workflow. Language models interpret answers; typed records and Python validators turn them into fields and screening decisions.

  1. Establish the basics

    Language selection, phone number, names, and the Virginia county or city where the issue arose. Service-area checks use configured locality data and FIPS identifiers.

  2. Understand the legal problem

    A weighted ensemble combines two model classifiers and keyword matching to suggest an LSC problem code. Uncertain classifications can prompt follow-up questions.

  3. Screen the household

    Adverse parties, domestic violence, adults and children, income sources and payment periods, benefits, and countable assets. The flow branches when configured screening rules fail.

  4. Prepare the handoff

    Citizenship, requested identifiers, additional names, address, and the case narrative complete the structured record. The project includes referral messaging and a LegalServer adapter; both external actions are disabled in this demo.

Rules are program-specific. The bundled income screen uses 300% of the poverty guideline. That is a configured project rule, not a statement that every LSC matter qualifies at that level. Reference data and program policies need ongoing review.

03 · SYSTEM ARCHITECTURE

One intake engine. Two entry points.

The public web demo wraps the existing Pipecat intake engine. The repository’s telephone path uses Daily PSTN and a Daily / Pipecat Cloud runtime.

Deployment and turn-taking details

The demo uses FastAPI, a TypeScript client, a single Fly Machine with 2 shared CPUs and 2 GB RAM, and no persistent database. Fly can stop it when idle and start it for a request. The demo caps sessions at ten minutes and allows two simultaneous conversations.

Voice activity and Smart Turn help decide when an answer ends; final speech transcripts feed the dialogue. Browser echo cancellation and rules requiring explicit user facts reduce accidental advancement. Real-room speaker echo and recognition errors can still occur. Automatic turn-taking remains enabled.

Latency includes speech recognition, end-of-turn detection, model generation, and speech synthesis. Keeping a machine warm removes startup delay but does not remove those per-turn costs. No production latency or accuracy benchmark is claimed here.

Other branches explore Deepgram / Flux and Cartesia and newer Pipecat versions. Those are alternative implementations, not providers selectable in this deployed demo; adopting them requires migration and regression testing.

04 · FROM INTAKE TO CASE SYSTEM

How it goes into LegalServer.

The repository has an API adapter, not just a transcript export. It validates a matter payload, creates the parent record, and uses the returned matter UUID for related records.

  "legal_problem_code": "63",
  "county_of_dispute": {
    "county_FIPS": "51031"
  },
  "number_of_adults": 2,
  "number_of_children": 1,
  "income_eligible": true
}

Selected fields from the fictional example, not a complete request or a record created by this demo.

  1. Create & validate

    Build a typed payload and POST to /matters. A successful response must include a matter UUID.

  2. Attach structured records

    POST to /matters/{uuid}/incomes, /adverse_parties, and /additional_names as applicable.

  3. Add the narrative

    POST case-description, asset, and applicable rejection notes to /matters/{uuid}/notes. The adapter logs a case-profile link when a case ID is available.

A handoff still needs review. Child writes happen after matter creation, so a partial failure can leave an incomplete record. The adapter logs failures and attempts fallback notes for some errors; it does not provide a durable transactional queue. Program-specific lookup fields and rejection policies need validation against the receiving LegalServer site. An unfinished intake without an address is currently mapped to “Other” rejection in the adapter.
Conflict checking: what is real, what is illustrated?

The core intake collects adverse parties for the LegalServer handoff. This page separately demonstrates an exact-name match against two invented records. It does not query LegalServer’s client database, perform a production conflict search, or decide whether representation is permitted. A production conflict workflow needs authorized data access and staff review.

05 · OPERATING CHOICES

Small when idle. Usage-driven when talking.

Compare infrastructure choices and change the assumptions. These are planning estimates in USD, not measured bills or a quote for a production service.

What is included in this estimate?

Recognition bills the full call duration in this example. Synthesis assumes the assistant speaks 40% of the time at 150 words per minute and 6 characters per word (including spaces): 3,600 characters in a ten-minute intake. The editable $0.05 model allowance covers the conversation and classifier ensemble together; it is a budgeting assumption, not token telemetry. Long prompts, repeated context, retries, reasoning tokens, and follow-ups can change it substantially.

Speech defaults ($1/hour and $15/million characters) are illustrative assumptions, not verified Azure account rates. Azure’s public pricing page did not expose numeric regional rates when checked. Replace these values with your region, voice, and agreement prices. Provider swaps require code changes; changing this calculator does not change the running demo.

Fly compute uses the published Ashburn shared-CPU-2x / 2 GB rate of $13.39 per 30-day month. The sleeping example includes an assumed 2 GB root filesystem at $0.15/GB/month, prorated for stopped time. Actual filesystem size and active hours vary; a container download size is not a root-filesystem measurement. Warm and two-machine examples run for all 720 hours.

Excluded: network egress, taxes, optional support, telephone / Daily / Pipecat Cloud charges, number rental, SMS, LegalServer licensing, implementation, security review, monitoring, and staff time. Free credits and volume discounts are not assumed. The two-machine estimate is a cost scenario, not an already-tested scaling configuration.

Sources checked October 17, 2026: Fly resource pricing · Azure Speech pricing and billing units · Azure model pricing · Daily / Pipecat Cloud pricing.
